# GA4（Google Analytics 4）の導入

## 背景

アプリには利用状況を測る仕組みが何もない。どのページが見られているか、
大会が実際に作られて当日に使われているのかが分からない。

計測の土台として GA4 を入れる。`gtag.js` の読み込みとページビュー送出は
自前の `GoogleAnalytics` コンポーネントが行う（経緯は「採用した方針と、
採らなかった方針」を参照）。

## ゴール

- 全ページのページビューが GA4 で計測される（クライアント遷移を含む）。
- 主要な操作がカスタムイベントとして送られる。
  `sign_up` / `login` / `create_organization` / `create_tournament` /
  `create_division` / `record_result` の 6 種。
- 測定 ID が未設定の環境では、スクリプトもイベントも一切出ない。
- GA へ送る `page_location` にクエリ文字列は含まれず、個体を指す ID は
  `:id` に伏せられる。

## 非ゴール

- Cookie 同意バナー、Consent Mode v2 の実装。
- 管理画面（`/orgs/...`）と公開ページ（`/t/...`）の GA プロパティ分離。
  今回は 1 プロパティで両方を計測する。
- サーバ側の Measurement Protocol による送信。
- Google ログイン経路の計測（理由は「認証イベント」の節）。
- 6 種以外のイベント（エントリー追加、組み合わせ生成、スケジュール編集など）。

## 全体の流れ

```
app/layout.tsx （Server Component）
  └─ gaMeasurementId()            ← src/shared/lib/analytics/ga-id.ts
       ├─ null  → 何も描画しない
       └─ "G-…" → <GoogleAnalytics gaId={id} />   （src/components/analytics/GoogleAnalytics.tsx）
              └─ usePathname() の変化ごとに
                 sendGtagEvent("page_view", { page_location: … })
                 page_location はクエリを落とし ID を :id に伏せた path
                 （src/shared/lib/analytics/sanitize-url.ts）

各クライアントコンポーネント
  └─ trackEvent(name, params)     ← src/shared/lib/analytics/events.ts
       └─ sendGtagEvent(name, params)  ← src/shared/lib/analytics/gtag.ts
            └─ gaMeasurementId() === null → no-op
```

DB 変更・マイグレーションは不要。

## 採用した方針と、採らなかった方針

**採用**: `next/script` による自前の `gtag.js` ブートストラップ
（`src/components/analytics/GoogleAnalytics.tsx` / `src/shared/lib/analytics/gtag.ts`）。
ページビューは `config` に任せず、`usePathname` の変化ごとに
`page_location` を `sanitizePagePath`（クエリを落とし、個体を指す ID を
`:id` に伏せる）に通してから自前で送る。

**採らなかった案 1（当初の採用案）**: `@next/third-parties` の
`GoogleAnalytics` コンポーネント。`next` 16.3.3 に対して系列の揃う
16.3.4 が公開されており、`gtag.js` を hydration 後に読み込む最適化と
`sendGAEvent` が付いてくるため、当初はこちらを採用していた。

しかしこのコンポーネントは `gtag('config', ...)` に `debugMode` 以外の
追加パラメータを渡す口を持たず（`node_modules/@next/third-parties/dist/google/ga.js`）、
`config` 呼び出しが即座に `page_location`（クエリ込みの完全 URL）で最初の
`page_view` を送ってしまう。差し替える隙が無いため、`/reset-password?token=<token>`
のようなページ（パスワード再設定、`2026-09-08-password-reset-design.md`）が
実装されると、有効なトークンが GA に送られ管理画面から閲覧・保存され続ける。
GA4 は既定では任意のクエリ文字列を除去しないため、これは公式パッケージのまま
では塞げない。この理由だけで自前実装へ切り替えた。

**採らなかった案 2**: Google Tag Manager コンテナを入れ、GA4 の設定を GTM 画面側で行う。
将来ほかのタグも足すなら有利だが、いま必要なのは GA4 だけで、
設定がリポジトリの外に出て「コードを読んでも何を計測しているか分からない」状態になる。

## 測定 ID の扱い

```ts
// src/shared/lib/analytics/ga-id.ts
/** 測定 ID。未設定・空文字なら null（＝一切計測しない）。 */
export const gaMeasurementId = (): string | null => {
  const id = process.env.NEXT_PUBLIC_GA_ID;
  return id !== undefined && id !== "" ? id : null;
};
```

`NEXT_PUBLIC_*` はビルド時に文字列リテラルへ静的置換される。
`process.env[key]` のような動的アクセスは置換されず `undefined` になるため、
必ず `process.env.NEXT_PUBLIC_GA_ID` と直書きする。

`.env.example` に以下を追記する。

```
# Google Analytics 4 の測定 ID（G- で始まる）。
# 空または未設定のとき、gtag.js の読み込みもイベント送信も一切行わない。
# ローカル開発では空のままにしておき、本番の値を混ぜないこと。
#
# 【重要】このアプリは page_view を自前で送る（クエリ文字列を落とし、
# ID を :id に伏せた path だけを送る）。GA4 プロパティの拡張計測から
# 「ブラウザの履歴イベントに基づくページの変更」を必ずオフにすること。
# オンのままだと GA が素の URL でも page_view を送り、
# /reset-password?token=... のようなページでトークンが Google に保存される。
NEXT_PUBLIC_GA_ID=""
```

この運用上の前提（拡張計測の当該項目をオフにすること）は、コードでは強制
できないプロパティ側の設定である。「GA プロパティの手動設定」の節にも
まとめて書く。

`NODE_ENV` では分岐しない。測定 ID の有無だけが有効・無効を決める唯一の条件で、
ステージング用のプロパティを使いたいときにそのまま対応できる。

## イベント送信の共通ラッパー

```ts
// src/shared/lib/analytics/events.ts
export type AnalyticsEvent =
  | "sign_up"
  | "login"
  | "create_organization"
  | "create_tournament"
  | "create_division"
  | "record_result";

export const trackEvent = (
  name: AnalyticsEvent,
  params?: Record<string, string>,
): void => {
  sendGtagEvent(name, params ?? {});
};
```

`sign_up` / `login` / `record_result` は動詞先頭の GA4 推奨イベント名の
流儀にもとから合っていた。作成系の 3 つは当初 `organization_create` の
ように名詞先頭で付けており、GA4 のイベント一覧で 2 つの流儀が混在して
いたため、データを貯め始める前に `create_organization` へ改名して揃えた。
`sign_up` と `login` はレポート側の既定イベントに紐づくため改名の対象外。

`sendGtagEvent`（`src/shared/lib/analytics/gtag.ts`）を直接呼ばずこの
ラッパーを挟む理由は 3 つ。

1. イベント名がユニオン型で一箇所にまとまる。タイポは型エラーで落ちる。
   GA4 は未知のイベント名も受け付けてしまうため、送信後には気づけない。
2. 測定 ID が無いとき `window.dataLayer` に触らない。テストとローカル開発で
   グローバルが汚れない（この判定は `sendGtagEvent` 側が持つ）。
3. テストのモック点が 1 箇所に定まる。

`gtag.ts` はクライアント専用なので、`events.ts` を import してよいのは
`"use client"` のコンポーネントだけである。

## GA へ送る URL のサニタイズ

`page_location` は既定では現在の URL をそのまま（クエリ文字列込みで）送る仕様である。
このアプリにはパスワード再設定 `/reset-password?token=<token>`
（`2026-09-08-password-reset-design.md`）のように、クエリに一度きりの
秘密を載せるページがある。GA4 は既定では任意のクエリ文字列を除去しない
ため、素の URL を送るとトークンが Google 側に保存され続けてしまう。

`sanitizePagePath`（`src/shared/lib/analytics/sanitize-url.ts`）が
`page_location` を組み立てる前に通る。クエリ文字列をすべて落とし、
パスのうち個体を指す ID を `:id` に置き換える。ID を伏せるのは秘匿目的に
加えて、大会・部門ごとに 1 行に分散してしまうページ別レポートを画面単位で
集約して読めるようにするためでもある。

**判定は主にパスの位置で行う。** `tournaments` `divisions` `users` `t` の
直後のセグメントを ID とみなし、`new` `edit` のような画面名だけ例外にする。
見た目（長さや文字種）だけで判定すると、`validateSlug` が許す 16 文字以上の
英数字だけの組織 slug や数字だけの slug まで `:id` に潰れ、「どの組織で
使われているか」という肝心の指標が消えてしまう。

ただし位置だけだと、後から `/invite/<token>` のようなルートが増えたときに
誰かが表へ足すまで素通りする（fail-open）。そこで形が UUID か cuid の
セグメントも伏せる保険を重ねてある。`/orgs` の直後だけは slug 確定なので
保険を効かせない。なお `t` `users` `tournaments` `divisions` は
`RESERVED_SLUGS` に入れて組織 slug として使えないようにしてある。
使えると位置ベースの判定とぶつかって集計がずれるためである。

**`page_location` はすべてのヒットに載せる。** `page_view` のイベント引数と
してだけ渡す作りでは足りない。gtag は指定の無いヒットに
`document.location.href` を自分で載せるため、`login` や `record_result` が
素のクエリ付き URL を送ってしまう（実測で `?token=...` がそのまま飛ぶことを
確認した）。`config` と `set` の既定値に入れ、さらに `sendGtagEvent` が
各イベントにも明示的に載せる。

**`page_referrer` も塞ぐ。** ここを見落とすと、`page_location` を塞いでも
1 つ隣の項目から同じ漏れが起きる。gtag は指定が無ければ `document.referrer`
を載せ、ブラウザ既定の `strict-origin-when-cross-origin` では同一オリジンの
遷移でクエリ込みの完全 URL が入る。`/reset-password?token=...` からページを
移動しただけで、次のヒットの参照元としてトークンが飛ぶ（実測で
`dr=...?token=...` を確認した）。同一オリジンの参照元だけサニタイズし、
外部からの流入は流入元の分析に要るのでそのまま通す。

**`page_title` も同じ理由で伏せ、サニタイズ済みのパスを送る。** gtag は
`document.title` を自動で付ける。`/t/**` は参加者の本名や大会名を出すため
`robots: noindex` にしてあるのに、タイトルをそのまま送ると「Google に
渡さないと決めた名前」を GA 経由で渡すことになる。パスと揃えておけば
レポートは画面単位で読め、名前は出ない。

`page_view` の送出経路は `GoogleAnalytics` コンポーネントの `useEffect`
（`usePathname` 依存）1 本のみで、初回描画とクライアント遷移の両方をここから
送る。`gtag('config', ...)` 由来の自動 `page_view` には頼らない。理由は
「採用した方針と、採らなかった方針」を参照。

## GA プロパティの手動設定（前提条件）

GA4 の拡張計測にある「ブラウザの履歴イベントに基づくページの変更」は
**プロパティ側で必ずオフにする**。このアプリは `page_view` を自前でしか
送らないため、この設定がオンのままだと GA 自身が素の URL のままもう一つ
`page_view` を送ってしまい、上記のサニタイズが意味を成さなくなる。
コードでは強制できない前提なので、`.env.example` の `NEXT_PUBLIC_GA_ID`
のコメントに同じ内容を書き、GA を有効化する人が必ず目にするようにしている。

## 認証イベント

- `SignupForm`: `setSentTo(parsed.data.email)` の直前で
  `trackEvent("sign_up", { method: "email" })`。
  仮登録（確認メール送信）の完了時点で撃つ。確認リンクを踏んだ本登録完了ではない。
  登録フォームはメールアドレスのみを受け付けるため `method` は常に `"email"`。
- `LoginForm`: ログイン成功後に
  `trackEvent("login", { method: parsed.data.identifier.kind })`。
  ログインフォームはメールアドレスとユーザー名の両方を受け付けるため、
  `method` は `"email"` 固定ではなく、実際に入力された識別子の種別
  （`"email"` または `"username"`、`src/features/auth/login/identifier.ts`
  の判定）をそのまま送る。

**Google 経路は計測しない。** `authClient.signIn.social` は成功するとブラウザを
Google の認証画面へ遷移させるため、クライアントは成否を観測できない。
押下時に撃つと、Google 側で中断した離脱も成功として計上される。
「成功時のみ送る」という本設計の原則を優先して、今回は送らない。

その結果、GA4 上の `login` / `sign_up` はメール経路のみの数になる。
Google 経路まで含めた実数が必要になった時点で、
コールバック先で撃つ（`?created=` と同じクエリ方式）などを別途検討する。

## 作成イベント

組織・大会・部門の作成ハンドラーはいずれも成功時に `redirect()` する。
`redirect` は例外を投げて制御を打ち切るため、`useActionState` の state は更新されず、
クライアントは「成功した」ことを観測できない。

そこで、リダイレクト先の URL にクエリを載せて成功を伝える。

| ハンドラー | リダイレクト先 |
| --- | --- |
| `features/organization/create/handler.ts` | `/orgs/{slug}?created=organization` |
| `features/tournament/create/handler.ts` | `/orgs/{slug}/tournaments/{id}?created=tournament` |
| `features/division/create/handler.ts` | `/orgs/{slug}/tournaments/{tid}/divisions/{id}?created=division` |

クエリの値（`organization` / `tournament` / `division`）とそれが表す GA
イベント名の対応は `src/shared/lib/analytics/created.ts` の
`CREATED_EVENTS` に 1 か所だけ持つ。ハンドラー側（クエリを吐く側）と
`TrackCreated`（読む側）が同じ定義を共有することで、どちらかを直したときの
直し忘れが型エラーとして出る。

遷移先のページに共通コンポーネントを置く。

```tsx
// src/components/analytics/TrackCreated.tsx
"use client";

export function TrackCreated({ created }: { created: string | undefined }) {
  const pathname = usePathname();
  const fired = useRef(false);

  useEffect(() => {
    if (created === undefined) return;
    if (fired.current) return;
    // URL は手で打てる。既知の値以外は無視し、イベント名が外部入力で汚れないようにする。
    const event = eventFor(created); // CREATED_EVENTS を引く
    if (event === undefined) return;

    fired.current = true;
    trackEvent(event);
    // クエリを消す。リロードや共有で二重に計上されるのを防ぐ。
    // router.replace は直前にサーバーコンポーネントが行ったのと同じ DB
    // クエリを即座に再実行してしまうため、履歴だけを書き換える
    // ネイティブの History API を使う。
    window.history.replaceState(null, "", pathname);
  }, [created, pathname]);

  return null;
}
```

`fired` の ref は React の開発時 StrictMode 対策である。`window.history.replaceState`
は History を書き換えるだけでサーバーコンポーネントを再描画させないため、
effect が setup → cleanup → setup と 2 回走っても `created` は同じ値のまま
2 回目も届く。ref が無いとイベントが二重に飛ぶ。本番の挙動は変わらない。

配置先は 3 ページ。いずれも `PageProps<...>` の `searchParams` を `await` して
`params.created` を渡す（`searchParams` は Next.js 16 では Promise）。

- `src/app/orgs/[slug]/page.tsx`
- `src/app/orgs/[slug]/tournaments/[tournamentId]/page.tsx`
- `src/app/orgs/[slug]/tournaments/[tournamentId]/divisions/[divisionId]/page.tsx`

3 ページとも現状 `params` しか分割代入していないので `searchParams` を足す。
いずれも既存のページテストが `searchParams: Promise.resolve({})` を渡しているため、
テスト側の呼び出しは変えなくてよい。

`?created=organization` を手打ちすれば誰でもイベントを 1 件増やせるが、
分析用途では許容する。クエリ方式を採ったのは、サーバ側 `redirect` の保証を
そのまま残したまま「成功時だけ 1 回」を確実に取れるためである。

## 結果登録イベント

`recordResultAction` は `redirect` せず、成功時に `{ error: null }` を返す。
これは `INITIAL_DIVISION_FORM_STATE` と同じ形なので、初期表示と区別がつかない。
さらに `MatchResultRow` は 1 行 1 フォームで、同じ行で結果の登録と訂正が繰り返される。
したがって真偽値では足りず、成功のたびに変わる値が要る。

`DivisionFormState` に成功カウンタを足す。

```ts
export type DivisionFormState = {
  error: string | null;
  notice?: string;
  confirm?: { message: string; value: string };
  /**
   * 成功のたびに 1 増える。初期状態（undefined）と成功状態を区別し、
   * 同じ行での連続した成功もそれぞれ検知できるようにするため。
   */
  succeeded?: number;
};
```

`recordResultAction` の成功時の戻り値を
`{ error: null, succeeded: (prevState.succeeded ?? 0) + 1 }` に変える。
オプショナル項目なので、`DivisionFormState` を共有する他スライスは無変更でよい。

**実際に書き込んだときだけ増やす。** `MatchResultRow` は確認ダイアログを
意図的に省いており、同じ試合の勝者ボタンをもう一度押す「再タップ」が
確認なしで通る正規の操作である。大会当日はこの再タップが普通に起きる。
このとき `recordResultInDb`（`repository.ts`）は勝者が変わらないと判定して
何も書き込まず、`{ recorded: false }` を返す。ハンドラーはこれを見て
`succeeded` を増やさずに前回値をそのまま持ち越す。

```ts
// src/features/division/record-result/handler.ts（末尾）
revalidateDivisionResults(slug, tournamentId, divisionId);
// 何も書いていないので増やさない。ただし値は持ち越す。undefined に
// 落とすとクライアント側のカウンタだけが 0 に戻り、次に本当に記録した
// ときの 1 が「前回発火した 3」を超えられず、イベントが黙って消える。
if (!exit.value.value.recorded) {
  return { error: null, succeeded: prevState.succeeded };
}
return { error: null, succeeded: (prevState.succeeded ?? 0) + 1 };
```

`recorded` は `RecordResultPort` の戻り値 `DivisionSetupOutcome<{ recorded: boolean }>`
の一部として repository から運ばれてくる。「変更なし」の分岐
（`repository.ts` の `unchanged` 判定）は `{ recorded: false }`、実際に
更新した分岐は `{ recorded: true }` を返す。

`MatchResultRow` は前回値を `useRef` で保持し、増えたときだけ撃つ。

```tsx
const succeeded = state.succeeded ?? 0;
const trackedRef = useRef(0);
useEffect(() => {
  if (succeeded > trackedRef.current) {
    trackedRef.current = succeeded;
    trackEvent("record_result");
  }
}, [succeeded]);
```

「取り消し」ボタンも同じ `recordResultAction` を通る。取り消しは値を
書き換える操作なので `recorded: true` になり、`record_result` に含まれる。
登録と取り消しの区別は今回は入れない。

組織・大会の作成ハンドラーには既存のハンドラーテストが無い。本設計は
リダイレクト先の文字列にクエリを足すだけなので、テストを新設せず
`TrackCreated` 側のテストで受け側の挙動を担保する。

結果登録の行のテストを `MatchResultRow` 専用ファイルではなく
`MatchResultList.test.tsx` に足すのは、行が必ずリスト経由で描画され、
`matchRow()` フィクスチャと `<ul>` の入れ子が既にそこにあるためである。

`RootLayout` は Server Component で、`GoogleAnalytics` の描画有無は
`gaMeasurementId()` の戻り値だけで決まるため、レンダリングテストは書かず
`ga-id.test.ts` でカバーする。`GoogleAnalytics` と `TrackCreated` はどちらも
StrictMode の二重 effect 対策で ref を持つため、テストでは「同じ値で
再描画・再実行しても 1 回しか発火しない」ことも確かめる。本番の挙動には
影響しないが、ステージング用の測定 ID を `next dev` に向けて動作確認する
運用を想定しているため、開発時の重複計上も潰しておく。
